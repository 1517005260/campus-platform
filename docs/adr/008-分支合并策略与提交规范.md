# ADR-008 分支、合并策略与提交规范

- 状态：已采纳（2026-11-02 修订：由主干开发改为 dev / main 双长期分支）
- 日期：2026-10-12
- 决策人：`haotian-ying`（运维）；修订经项目 owner `1517005260` 确认
- 相关需求：—

## 背景

任务书要求分支与合并策略明确、经合并请求评审、提交说明能对应需求、冲突由人处理、部署版本可追溯。main 的每个提交都会自动部署到测试环境，因此 main 需要一道由人把关的入口，而日常开发不应被这道关卡拖慢。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. Git Flow（develop、release、hotfix 分支） | 发布节奏清晰 | 对 6 人、持续部署的项目过重 |
| B. 主干开发 + 短期功能分支，squash 合并 | main 历史中一个提交对应一个 PR | 每次合并都直接部署，所有合并都需要严格评审，日常开发慢 |
| C. dev / main 双长期分支 | 日常开发在 dev 上自由提交与合并；main 只由 owner 经 PR 合入，合并即发布到测试环境 | 需要在发布后把 main 同步回 dev |

## 决定

采用 C。

- `dev`：长期开发分支。有写权限的协作者可直接提交，也可从功能分支发 PR 合入；禁止删除和强推。
- `main`：只能经 PR 更新，按约定只从 `dev` 发起；只有项目 owner 能合并，使用 merge commit 保留 dev 历史；禁止删除和强推。
- 发布后将 main 的合并提交快进同步回 dev。规则与同步步骤见 `docs/plans/2026-10-22-dev-main-design.md`。
- 分支命名：`<类型>/<模块>-<需求编号>-<简述>`。
- 提交与 PR 标题：`<类型>(<范围>): <说明> [<需求编号>]`，类型取 feat / fix / refactor / test / docs / chore / ci。
- 版本：测试环境镜像以提交号为标签；生产以 `vX.Y.Z` 标签发布，Release Notes 自动列出包含的 PR。

## 后果

- CI 在 dev 上运行；dev → main 的 PR 直接复用 dev 上同一提交的检查结果，合并后部署流程不再重跑 CI。
- 每个功能分支保持小而短（1–2 天），减少冲突。
- 冲突由提交者手工解决，不交给 AI 自动合并。
