# ADR-001 公共层 D 的归属

- 状态：提议（项目启动会讨论后改为"已采纳"）
- 日期：2026-10-12
- 决策人：全员（C 主持）
- 相关需求：REQ-D-01 至 REQ-D-09

## 背景

任务书要求公共层（RBAC、空间与座位主数据、通知、审计）的归属由组内决定，并权衡工作量均衡、契约治理、故障责任归属。

约束：6 人分 3 个模块组；M1 业务最重；所有模块都依赖身份与通知；空间主数据与座位状态紧密耦合。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 全部归 M1 | M1 已经要维护座位，主数据集中 | M1 工作量过重；M1 故障时全系统无法登录 |
| B. 单独成立公共层组（2 人） | 职责清晰 | 只剩 2 个业务组，不满足至少 3 个模块组；公共层组没有业务代码 |
| C. 按子域拆给三个模块组，各自放在本模块服务里（AI 的首个方案） | 工作量均衡 | 鉴权放在 M2 服务里，M2 故障时其他模块无法登录；故障归属混乱 |
| D. 按子域拆：空间与座位主数据归 M1；RBAC、通知、审计组成独立的 common 服务，由 M2 组的 D 和 M3 组的 F 分别负责 | 工作量均衡；common 独立部署，故障影响范围清晰；座位状态唯一写入方在 M1 | 多一个服务要部署；D、F 同时服务两个模块 |

## 决定

采用方案 D。在按服务独立部署的前提下，C 把 RBAC 放在 M2 服务里，M2 故障会导致全系统无法登录，故障归属也不清晰。

- 空间与座位主数据归 M1：座位状态必须由 M1 唯一写入（任务书要求记录写入来源），主数据与状态放在一起才能用数据库约束保证一致。
- RBAC 由 D 负责：M2 的权限门槛和多级审批最依赖角色体系。
- 通知与审计由 F 负责：M3 业务相对 M1 轻，用公共层平衡工作量；F 同时负责集成契约，通知和审计是所有模块都要接入的契约。
- common 独立部署：JWT 由各服务本地校验，common 故障只影响新登录，不影响已登录用户。

## 后果

- 部署单元为 4 个后端服务。
- D、F 的代码改动涉及两个目录，CODEOWNERS 中两人都是 common 的负责人。
- 公共库 `libs/campus_common` 由 D、F 共同维护，改动需要评审。
