# ADR-001 公共层 D 的归属

- 状态：提议
- 日期：2026-11-05（初版 2026-10-12，按调整后的分工重写；初版内容见 git 历史）
- 决策人：全员；由项目 owner `1517005260` 提出
- 相关需求：REQ-D-01 至 REQ-D-09

## 背景

任务书要求公共层 D（RBAC 身份与权限、空间与座位主数据、通知服务、操作审计）的归属由项目组自行决定，权衡工作量均衡、契约治理、故障责任归属，并形成书面决策记录，说明采用什么方案、考虑了什么、依据是什么、如何达成组内一致。

初版按"3 个模块组各 2 人"设计，把 common 服务拆给 M2 组和 M3 组各一人兼管（RBAC、通知审计）。分工调整后，6 人各负责一块：common 与公共库、M1、M2、M3、前端、DSH 附加项与运维（见 `docs/process.md` 第 1 节），初版的前提不再成立：

- 不再有"模块组里分出一人兼管公共层"的人员结构。
- 公共库 `libs/campus_common` 已承担四个服务的共性能力（应用工厂、鉴权、时间、消息、幂等、迁移、测试插件），它和 common 服务的改动影响所有模块，需要一个明确的评审人。
- 两人分管 common 时，`auth.py` 与 `outbox.py` 等跨越两人边界的改动需要协调，故障也要先判断归谁。

不变的约束：座位状态由 M1 唯一写入（任务书要求记录写入来源），空间与座位主数据和座位状态放在一起；所有模块都依赖身份与通知。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 公共层全部并入 M1（含 RBAC、通知、审计） | 空间主数据与身份在同一人手里 | M1 工作量过重；M1 故障时全系统无法登录，评审积压会阻塞所有模块 |
| B. 按子域拆给各模块负责人，各自放在本模块服务里（初版讨论中 AI 的首个方案） | 不需要额外的负责人 | 鉴权放在某个业务服务里，该服务故障时其他模块无法登录；故障归属混乱 |
| C. 独立的 common 服务，由 M2、M3 负责人分别兼管 RBAC 与通知审计（初版的决定） | common 独立部署，故障影响范围清晰 | 模块负责人各自业务已满；公共层改动跨两人，评审与故障归属不清 |
| D. 独立的 common 服务与公共库由专职成员负责；空间与座位主数据仍归 M1 | 公共层有唯一负责人，契约治理与故障归属清晰；各业务负责人专注本模块 | 公共层评审集中在一人，可能成为瓶颈；该成员没有业务模块 |

## 决定

采用方案 D。

- common 服务（登录与 RBAC、院系、通知、审计、消息消费者）与公共库 `libs/campus_common` 由 `1517005260` 负责；公共库新增能力、跨模块契约（`contracts/`、`campus_common/events.py`）和集成测试由其评审。
- 空间与座位主数据归 M1（`cyuanb`）：座位状态的唯一写入方需要和主数据放在一起，才能用数据库约束保证一致。
- common 独立部署：JWT 由各服务本地校验，common 故障只影响新登录、通知与审计落库，不影响已登录用户使用业务功能。

决定性的理由是故障与评审责任归属：公共层的改动影响全部服务，需要一个固定的负责人；分工调整后恰好有一名成员不负责业务模块。

## 后果

- 部署单元为 4 个后端服务。
- 根 `AGENTS.md`"公共函数优先"中"公共库缺少某项能力时提出加入公共库"的评审人为 `1517005260`；`services/common/AGENTS.md`、`docs/design/common.md`、`README.md` 一致。
- 公共层评审集中在一人。若出现积压，再指定一名备份评审人并修订本 ADR。
- `1517005260` 同时是仓库 owner，但不是组长；组长另行确定（`docs/process.md` 第 1 节）。
