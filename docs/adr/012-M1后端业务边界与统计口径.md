# ADR-012 M1 后端业务边界与统计口径

## 背景

M1 的设计文档保留了若干未决问题，同时现有实现需要在以下方面形成一致口径：

- 是否限制最远提前预约天数。
- 是否限制每人每天的总预约时长。
- 签到窗口的精确边界。
- 座位状态日志在管理员停用、签到和占用场景下记录什么。
- 运营统计中的利用率、违约率和可用小时如何计算。

这些问题会直接影响接口校验、数据库查询、定时任务和测试边界，因此需要在批量实现前固定。

## 备选方案

### 最远预约天数

| 方案 | 做法 | 取舍 |
|---|---|---|
| A | 不增加限制 | 保持任务书范围，不扩大契约；远期资源无法提前保护 |
| B | 增加 `advance_days_max` 参数 | 能保护远期资源；增加接口字段、前端类型和测试范围 |

### 每日总预约时长

| 方案 | 做法 | 取舍 |
|---|---|---|
| A | 不增加限制 | 与任务书一致；连续预约可能绕过单次 4 小时限制 |
| B | 限制每人每日总时长 | 更符合减少疲劳的目标；规则和参数尚未定义，可能误伤学生 |

### 签到窗口

| 方案 | 做法 | 取舍 |
|---|---|---|
| A | 开始前 15 分钟至 `start_at + auto_cancel_min` 之前 | 与任务书、设计文档和未签到扫描一致 |
| B | 截止时刻仍允许签到 | 对边界用户更宽松；可能与未签到扫描并发成功 |

### 运营统计

| 方案 | 做法 | 取舍 |
|---|---|---|
| A | 已签到小时 / 有效开放座位小时 | 能反映实际使用率；历史配置无法精确还原 |
| B | 预约小时 / 开放小时 | 计算简单；未签到的占座会虚增利用率 |

## 决定

采用以下 M1 v1 口径：

1. 不增加最远提前预约天数限制。
2. 不增加每人每天总预约时长限制。
3. 签到窗口为开始前 15 分钟至开始后 `auto_cancel_min` 分钟之前；到达截止时刻后由未签到扫描取消。
4. 状态日志记录座位可用性变化：预约创建记为 `reserved`，释放记为 `released`，管理员停用、M2 占用和 M3 维修下架记为 `blocked`，重新启用或释放记为 `unblocked`；签到不额外写日志。
5. 利用率使用已签到预约小时数除以有效开放座位小时数。
6. 违约率使用 `no_show / (no_show + completed)`，分母为 0 时返回 0。
7. 按小时分布使用各整点有效签到座位小时数除以该整点有效开放座位小时数。
8. 统计只返回聚合数据，不返回学生个人自习轨迹。

v1 不实现最远预约天数和每日总时长限制，但连续预约绕过疲劳目标的问题保留在需求与伦理讨论中，不从未完成清单中删除。

## 后果

- M1 不需要为上述两个额外限制修改 `SeatSettings` 或前端类型。
- 搜索、可用性、预约创建和签到测试可以围绕固定边界编写。
- 统计只按当前启用座位计算历史开放小时；精确历史统计需要未来增加配置时间序列。
- 签到码暴力尝试、自动取消误判和违约申诉仍未解决，继续记录为伦理风险。

## 补充决定（2026-11-05）：停用座位、停用或注销自习室时的已有预约

### 背景

任务书只规定"自习室与座位的登记、注销、可用性维护由管理员统一管理"，没有说明停用或注销时已有预约如何处理。`rooms.is_study_room` 表示教室是否作为自习室开放，把它从 true 改为 false 就是注销自习室。原实现停用后只阻止新预约，已有预约保持有效：学生仍能在停用的座位上签到，停用形同虚设；注销自习室时也一样。

### 备选方案

| 方案 | 做法 | 取舍 |
|---|---|---|
| A | 只阻止新预约，已有预约照常使用 | 改动最小；停用的座位仍被使用，与"不可用"矛盾 |
| B | 取消尚未结束的有效预约，通知学生，不记违约 | 与整室占用（INT-04）处理一致；学生的预约会被动取消 |
| C | 有尚未结束的预约时拒绝停用 | 不打扰学生；座位损坏等情况管理员无法及时下架 |

### 决定

采用 B，由项目 owner `1517005260` 确定。

- 停用座位：该座位上 `end_at` 晚于停用时刻的 booked / checked_in 预约改为 cancelled，`cancel_reason = ADMIN_DISABLED`；停用教室或注销自习室（`is_study_room` 由 true 改为 false）：该教室全部座位同样处理。三种情况走同一条取消路径，使用同一个 `cancel_reason` 和事件 reason；判断教室是否可用的条件只有一处（`app/shared.py` 的 `room_usable()`：启用且是自习室）。
- 不记违约；写 `released` 状态日志（来源 `M1_ADMIN`，`ref_id` 为预约 ID）；通过 outbox 通知学生（`seat.reservation_cancelled_by_admin`），并发 `m1.reservation.cancelled(reason=ADMIN)`。取消动作与整室占用共用 `app/shared.py` 的 `release_reservation()`。
- 停用与新预约都先锁教室行，停用之后不会再有预约落到该座位上。重新启用或重新登记为自习室（false → true）不恢复已取消的预约，也不改动其他预约。

### 后果

- `campus_common.events.ReservationCancelled.reason` 增加 `ADMIN`（向后兼容的新增取值）。
- 被动取消会影响学生，通知中应说明原因；是否需要给出替代座位，留待需求评审。
