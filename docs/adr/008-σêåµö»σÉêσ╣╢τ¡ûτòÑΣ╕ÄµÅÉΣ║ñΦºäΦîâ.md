# ADR-008 分支、合并策略与提交规范

- 状态：提议（项目启动会讨论后改为"已采纳"）
- 日期：2026-10-12
- 决策人：E
- 相关需求：—

## 背景

任务书要求分支与合并策略明确、经合并请求评审、提交说明能对应需求、冲突由人处理、部署版本可追溯。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. Git Flow（develop、release 分支） | 发布节奏清晰 | 对 6 人、持续部署的项目过重 |
| B. 主干开发 + 短期功能分支，squash 合并 | main 历史中一个提交对应一个 PR，容易追溯；配合持续部署 | 功能分支内的细粒度提交在 main 上被压缩（PR 中仍可查看） |
| C. 主干开发 + merge commit | 保留全部提交 | main 历史杂乱 |

## 决定

采用 B。

- `main` 受保护：必须经 PR、`ci-passed` 通过、1 人批准、CODEOWNERS 批准，禁止强制推送。
- 分支命名：`<类型>/<模块>-<需求编号>-<简述>`。
- 提交与 PR 标题：`<类型>(<范围>): <说明> [<需求编号>]`，类型取 feat / fix / refactor / test / docs / chore / ci。
- 版本：测试环境镜像以提交号为标签；生产以 `vX.Y.Z` 标签发布，Release Notes 自动列出包含的 PR。

## 后果

- 每个功能分支保持小而短（1–2 天），减少冲突。
- 冲突由提交者手工解决，不交给 AI 自动合并。

## 达成一致的过程

待项目启动会填写：讨论时间、参与人、各方意见、最终决定方式。
