# ADR-004 定时任务与并发控制

- 状态：提议（项目启动会讨论后改为"已采纳"）
- 日期：2026-10-12
- 决策人：A
- 相关需求：REQ-M1-07/08/09、REQ-M2-05、REQ-M3-07

## 背景

M1 的提醒和自动取消、M2 的超时撤销、M3 的超时升级都要按时执行。要求：服务重启不丢任务、多个 worker 不重复执行、与用户操作（签到、审批）并发时结果正确。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 每个服务内置 APScheduler（AI 在规划阶段的首个推荐） | 不需要额外组件 | 多实例时重复执行；重启后内存中的任务丢失 |
| B. 每条预约投递 Celery 延时任务（eta/countdown） | 到点精确 | 预约取消或修改时要撤销任务，难以做对；broker 重启或任务丢失时不一致 |
| C. Celery Beat 定期触发扫描任务，数据库 SKIP LOCKED 抢行 + 状态条件更新 | 状态全在数据库，可重复执行，重启自动补偿 | 精度取决于扫描间隔（1 分钟）；需要合适的索引 |

## 决定

采用 C。约束是多实例、重启、并发下都不冲突：A 简单，但单条延时任务在预约取消或修改后难以撤销，重启或多实例时也难以保证只执行一次。Beat 只负责按时投递扫描任务，每个环境每个服务一个 Beat；任务用 Redis 锁避免同一扫描并发执行；正确性由数据库保证（行锁、状态条件、唯一约束）。每个服务的 Celery 任务使用以服务名命名的队列。

并发冲突尽量交给数据库：座位与用户时段重叠用排除约束；状态迁移用条件更新或乐观锁；幂等用唯一键与咨询锁。
