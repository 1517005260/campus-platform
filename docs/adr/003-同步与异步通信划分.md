# ADR-003 同步与异步通信的划分

- 状态：提议（项目启动会讨论后改为"已采纳"）
- 日期：2026-10-12
- 决策人：F
- 相关需求：INT-01 至 INT-07、REQ-D-05、REQ-D-07

## 背景

模块之间既有"马上要结果"的调用（维修开始时座位必须立即下架），也有"告诉一声即可"的事件（发通知、记审计）。全部同步调用会让通知服务的故障拖垮业务；全部异步又无法满足即时下架。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 全部同步 HTTP | 简单、好调试 | common 不可用时所有业务失败 |
| B. 全部消息驱动（含占用、释放） | 解耦彻底 | 占用结果（被取消的预约）无法同步返回；演示"模块 A 网络调用模块 B"不直观；最终一致带来的中间状态难以解释 |
| C. 命令同步 + 事件异步 | 各取所长 | 需要同时维护 HTTP 与消息两套契约 |

## 决定

采用 C。

- 同步 HTTP（带幂等键）：M2/M3 → M1 占用与释放；查询类调用。
- RabbitMQ 消息：`notification.send`、`audit.record`、各模块领域事件。生产端用 outbox 与业务同事务写入，消费端用 inbox 去重，失败进入死信队列。
- 失败策略：调用方先调远端、成功后再提交本地；远端失败时本地不变：远端不可达或拒绝服务间调用返回 502，远端的业务错误（400/404/409）原样返回，由调用方按错误码处理。

## 后果

- 消息契约在 `contracts/events/`，与 OpenAPI 一起做漂移检查。
- 先调远端再提交本地，存在"远端成功、本地提交失败"的窗口：M2 用补偿释放处理；M3 依赖幂等键重试。更彻底的做法（本地先记"待占用"状态，异步驱动远端）留作后续改进。
