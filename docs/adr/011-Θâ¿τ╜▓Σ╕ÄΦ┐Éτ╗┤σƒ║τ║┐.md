# ADR-011 部署与运维基线

- 状态：提议（项目启动会讨论后改为"已采纳"）
- 日期：2026-10-15
- 决策人：E
- 相关需求：非功能需求（可部署、可回滚、可观测、安全）；补充 [ADR-007](007-数据库schema划分与迁移规范.md)、[ADR-010](010-消息拓扑与失败重试.md)

## 背景

测试与生产环境用同一份 `deploy/docker-compose.yml` 部署在单机 Docker 上，由流水线自动发布。需要一套统一的基线，回答：密钥与权限怎么给、进程按什么顺序启动、怎样判断健康、发布前要满足什么条件、出问题怎样回滚，以及开发环境与部署环境的边界。目标是每一条都由配置或代码保证，而不是依赖操作者记得。

## 决定

### 配置、密钥与权限

| 项 | 做法 |
|---|---|
| 配置来源 | 非敏感配置在 `deploy/env/<环境>.env`（纳入版本管理）；密钥清单与默认值在仓库根目录的 `.env.example`（纳入版本管理），本地修改写在 `.env`（不纳入版本管理）。`scripts/deploy.sh` 按"同名环境变量（GitHub 环境 secrets）> `.env` > `.env.example`"取值，合成服务器上的 `.env`（值用单引号包裹，按原样传入），权限 600 |
| 缺失即失败 | compose 对必需变量使用 `${VAR:?说明}`，缺少时拒绝启动，不会以空密钥运行 |
| 密钥默认值 | 不配置任何密钥即可部署：数据库、RabbitMQ、管理员与演示账号密码使用一套简单的默认值，便于课程演示；JWT 签名密钥与服务间密钥（`.env.example` 中 `@random-if-empty` 标记的项）默认留空，部署时在服务器上生成随机值并保存在部署目录的 `.secrets.generated`，之后沿用（这类密钥没有人需要记住，公开值会让任何人都能伪造 token）；外部服务密钥（如 `SMTP_PASSWORD`）留空表示不使用。`scripts/gen_secrets.sh` 可把密码与签名密钥换成随机值；数据库与 RabbitMQ 密码在环境首次部署时固定，随机化应在首次部署前进行 |
| 数据库 | 每个服务独立角色，只拥有自己的 schema（ADR-007）；CI 与本地测试同样以服务角色运行，权限问题在合并前暴露 |
| 消息 | 业务进程使用业务账号：无管理标签，只能声明平台自己的资源（`campus.*`、`common.*` 与各服务的 Celery 队列，见 `topology.APP_CONFIGURE_PATTERN`）；管理员账号只给一次性容器 `mq-setup` |
| 进程配置 | 每个进程只拿到自己需要的环境变量：JWT 密钥、演示账号与引导管理员密码只给 api；服务间调用只有 M2、M3 → M1、M2、M3 → common 两类，因此只有 M2、M3 持有调用密钥，`SERVICE_KEYS`（允许调用本服务 `/internal` 接口的服务及其密钥）只给 M1、common 的 api；SMTP 配置只给 common-worker；beat 只拿到 broker 与 Redis 地址 |
| 初始账号 | 所有环境由种子写入引导管理员 `admin`（`ADMIN_PASSWORD`），新环境部署后即可登录并创建用户；测试环境 `SEED_DEMO=true` 另写入演示账号（`DEMO_PASSWORD`），集成测试读取同一个值 |
| 进程身份 | 业务镜像以 uid 10001 的非 root 用户运行；前端与网关使用 `nginx-unprivileged`（监听 8080） |
| 网络暴露 | 只有网关发布端口。Docker 发布的端口绕过 ufw，因此其他端口一律绑定 127.0.0.1（如 Mailpit 界面），开发环境同样只绑定本机。容器之间共用一个内网，内部服务依靠各自的账号与密钥认证 |
| SSH 与服务器 | 服务器指纹预先核对后存入 `DEPLOY_KNOWN_HOSTS`，流水线不在部署时临时信任；`server_init.sh` 配置公钥后关闭密码登录。部署用户属于 docker 组，等同 root：单服务器方案中测试环境的部署密钥同样能触及生产，因此 test 环境只允许 main 使用，需要更强隔离时测试与生产使用不同服务器 |
| 流水线 | 工作流默认只读，按任务授予权限（推送镜像、创建 Release 的任务才有写权限）；发到服务器的镜像仓库令牌只能拉取，远程脚本退出时（无论成败）登出；Actions 按提交 SHA 固定；用户输入经环境变量传入脚本，不直接拼接进命令；必需检查 `ci-passed` 限定来自 GitHub Actions |

### 启动顺序与健康检查

```
postgres / redis / rabbitmq（健康）
  → mq-setup（一次性：拓扑、policy、业务账号；成功退出）
  → 各 api（迁移 → 种子 → /ready 通过）
  → worker / beat / consumer
  → 前端（/healthz）→ 网关（/healthz）
```

| 进程 | 健康检查 | 说明 |
|---|---|---|
| api | `GET /ready` | 数据库可用才算就绪；`/health` 只表示进程存活 |
| worker | `celery inspect ping` | 与 broker 断开时失败 |
| consumer | `GET /health`（8090） | broker 连接可用且队列自检正常；自检发现队列缺失或无消费者时重建拓扑并退出，由重启策略拉起 |
| beat | 无 | 进程退出即容器退出，由 `restart: unless-stopped` 拉起 |
| 前端、网关 | `GET /healthz` | |

健康检查一律访问 `127.0.0.1`，不依赖容器内 `localhost` 的解析顺序。健康状态用于启动顺序（`depends_on`）、部署等待（`--wait`）与排查；Docker 不会因为"不健康"重启容器，只有进程退出才由重启策略拉起，因此需要自愈的进程（consumer）在检测到异常时主动退出。

### 网关

- 路由表 `deploy/gateway/gateway.conf` 各环境共用；上游地址按环境定义：部署环境用 Docker DNS 动态解析（`resolve`），api 容器重建、IP 变化后无需重启网关；开发环境指向宿主机。
- 未匹配的 `/api/`、`/ops/` 路径直接返回 404，不落到前端。
- 网关是最外层入口，用对端地址设置 `X-Forwarded-For`，后端（`--forwarded-allow-ips`）据此记录真实来源，客户端无法伪造；只接受格式合法的 `X-Request-ID`，否则重新生成。
- 隐藏 nginx 版本号，添加 `X-Content-Type-Options`、`X-Frame-Options`、`Referrer-Policy` 响应头。

### 镜像与依赖

- 基础镜像、中间件与工具（postgres、redis、rabbitmq、nginx、mailpit、python、node、uv、oasdiff、mutmut）固定到具体版本；Python 版本由 `.python-version` 固定。Dependabot 每周为 Dockerfile、compose、Actions、Python 与前端依赖提升级 PR，经 CI 验证后合并；uv、oasdiff、mutmut 与 CI 中的 node 版本不在 Dependabot 的覆盖范围内，由 E 随依赖升级一并手动更新。
- RabbitMQ 固定主机名：节点数据目录按主机名区分，固定后容器重建不丢队列、消息、policy 与账号。
- 容器日志 json-file，20MB × 5 轮转。

### 邮件

- SMTP 完全由配置决定（`SMTP_HOST/PORT/USERNAME/PASSWORD/SECURITY`、`MAIL_FROM`），`SMTP_HOST` 为空表示只发站内信。
- 测试环境启用 compose profile `mailcatcher`，邮件进入 Mailpit；界面只绑定服务器本机，经 SSH 隧道查看。生产环境接入真实 SMTP，不运行 Mailpit。

### 发布与回滚

| 阶段 | 门禁 |
|---|---|
| 合并到 main | `ci-passed`；破坏性契约变更需 PR 标签，标签变化重新触发检查 |
| 测试环境 | 只有 main 能使用 test 环境；部署成功（`--wait` 全部健康）且跨模块集成测试通过后，镜像加 `verified-<提交号>` 标签。部署与手动集成测试（`integration-test.yml`）共用并发组，互不交错；排队中的部署被更新的提交取代时，被跳过的提交不会获得 verified 标签，发布时选用之后的提交 |
| 生产环境 | `v*` 标签只有仓库管理员能创建，创建后任何人（包括管理员）都不能修改或删除；未配置审批人时拒绝部署（仓库变量 `PROD_APPROVERS_CONFIGURED`）；只接受 main 上、带 `verified-<提交号>` 的镜像，打版本标签后经审批部署（审批人不能审批自己触发的部署）；版本标签由 `retag_images.sh` 保证不改指（镜像仓库本身不提供标签不可变）；部署后校验各服务 `/version` 的 `git_sha` 等于该标签的提交；部署成功后才创建 GitHub Release |
| 回滚 | 从 main 手动运行 `deploy-prod.yml` 并填写目标版本（必须是已成功发布、有 Release 的 vX.Y.Z，同样需审批）；部署使用该版本自己的配置。迁移遵循"先扩展后收缩"，api 启动时若数据库版本比镜像新则跳过迁移并告警，旧镜像直接运行在新 schema 上；需要降级数据库时由人确认数据影响后执行 |

### 备份

每次部署前与每日 03:00（`server_init.sh` 安装的 cron）执行 `deploy/backup.sh`：`pg_dump` 自定义格式写入部署目录的 `backups/`，部署前备份与每日备份各保留最近 14 份，恢复命令见脚本注释。备份只在本机，需要异地保存时另行同步。

### 开发环境

开发 compose 只运行依赖与网关，端口只绑定 127.0.0.1；网关经 `host.docker.internal` 访问本机进程。Docker Desktop 与 OrbStack 可访问本机回环地址，Linux 原生 Docker 需 `DEV_BIND_HOST=0.0.0.0`。

### 数据保留

- outbox 已发布的行保留 7 天，由投递任务定期清理；只有消息自身的错误（无法序列化等）跳过该条，broker 不可用、账号无权限等对每条消息都一样的错误整批停止。
- inbox 去重记录保留 30 天（长于延迟重试与死信重放的时间窗口），由 common 的每日任务清理。

## 后果

- 新服务或新进程必须声明健康检查、只拿自己需要的密钥、以非 root 运行；新增密钥时登记在 `.env.example`（给出默认值，签名类密钥加入 `@random-if-empty`），compose 中使用 `${VAR:?}`。
- 依赖 Docker DNS 动态解析要求网关镜像为 nginx ≥ 1.27.3。
- 以下限制在课程项目规模下接受，记录在风险清单：所有业务进程共用一个 RabbitMQ 业务账号（可读写彼此的队列）；Postgres 容器在整个生命周期保留初始化用的密码环境变量；Redis 未设置密码，只在容器内网可达。
- 发布流程多了一个"验证标签"步骤：没有在测试环境通过集成测试的提交不能发布到生产。
- 回滚不自动降级数据库，因此每次 schema 变更都必须保持向后兼容一个版本（ADR-007 已要求）。
- 网关目前只提供 HTTP。服务器与域名确定后在网关启用 HTTPS（证书、HTTP 跳转、HSTS），在此之前测试环境经公网 IP 访问、只使用演示账号（风险 R-13、需求 NFR-08）。
