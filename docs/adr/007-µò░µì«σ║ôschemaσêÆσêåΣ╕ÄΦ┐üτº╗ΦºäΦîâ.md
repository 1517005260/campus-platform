# ADR-007 数据库 schema 划分与迁移规范

- 状态：提议（项目启动会讨论后改为"已采纳"）
- 日期：2026-10-12
- 决策人：A
- 相关需求：NFR-01、NFR-05

## 背景

任务书要求 schema 变更以版本化迁移提交、从空库可一次重放、禁止手工改库；跨模块不得直接访问数据库。四个模块并行开发，迁移不能互相冲突。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 一个数据库、一个 schema、一套迁移 | 简单 | 四组人改同一条迁移链，频繁冲突；无法从权限上隔离 |
| B. 每个服务一个独立数据库实例 | 隔离最彻底 | 资源占用高，部署复杂 |
| C. 一个数据库实例，每个服务一个 schema 和数据库角色，各自一套 Alembic 迁移 | 隔离可由数据库权限保证；迁移链互不干扰；只需一个 Postgres | 跨 schema 的一致性只能靠接口保证 |

## 决定

采用 C。Alembic 版本表放在各自 schema（`m1.alembic_version`）。迁移编号顺序递增（`0001`、`0002`…）。迁移遵循"先扩展后收缩"，保证回滚到上一版镜像时旧代码可运行。种子数据分基础与演示两类，均幂等。api 容器启动时执行迁移与种子。

## 后果

- CI 检查：空库重放、`alembic check`、回退再重放、种子执行两次。
- 同一服务两人同时生成迁移会出现两个 head，合并前由 A 协调重新编号。
