# 开发流程

本文规定 6 人小组如何分工、按什么节奏推进、每个任务怎样从需求走到生产，以及各评审节点和期末演示的准备。

## 1. 分工

每人负责一块业务代码，同时兼一个横向负责人角色。横向角色负责制定规范和兜底，不是一个人包办：每个人都在自己的模块里写迁移、写测试、提交代码。

| 成员 | 模块 | 业务职责 | 横向负责人 |
|---|---|---|---|
| A | M1 | 预约核心、空间与座位主数据、跨模块占用接口 | **数据演进**：迁移规范、种子数据、schema 变更评审 |
| B | M1 + 前端 | 前端 core 与 M1 页面、签到、提醒任务、运营统计 | **测试与质量**：测试分层、变异测试报告、质量门禁 |
| C | M2 | 申请、多级审批、超时撤销；**组长** | **需求与追踪**：需求基线、评审节点材料、伦理记录 |
| D | M2 + common | 资格门槛、审批配置；RBAC 与登录 | **AI 协作规范**：AGENTS.md、spec 模板、AI 代码审查清单（`docs/ai-review-checklist.md`） |
| E | M3 | 工单全流程 | **DevOps**：流水线、Docker、服务器、发布与回滚 |
| F | M3 + common | 超时升级、通知集成；通知与审计 | **集成与契约**：契约检查、集成测试、DSH 附加项 |

CODEOWNERS 按此分工配置（`.github/CODEOWNERS`），项目启动时把占位符换成真实 GitHub 用户名（见第 8 节）。

## 2. 阶段计划

```
阶段 0（第 1 周前 2 天）全员定契约
  → 阶段 1（第 1–3 周）6 人并行开发，依赖打桩
  → 第一次 Review（约第 4 周）
  → 阶段 2（第 4–8 周）并行开发 + 每周联调
  → 第二次 Review（约第 9 周）唯一硬性汇合点
  → 阶段 3（第 10–11 周）DSH 附加项 + 发布演练
  → 阶段 4（第 12 周）彩排与期末展示
```

### 阶段 0：定契约（本仓库即阶段 0 的产出）

| 步骤 | 内容 | 负责 |
|---|---|---|
| 0.1 | 建 Organization 和仓库，运行 `scripts/github_setup.sh` | E |
| 0.2 | 讨论并确认 `docs/adr/` 中的全部 ADR，把状态从"提议"改为"已采纳"，记录讨论方式 | C 主持，全员 |
| 0.3 | 逐个模块过一遍 `docs/design/*.md` 的接口清单，跨模块接口由提供方和调用方共同确认 | F 主持 |
| 0.4 | 确认需求基线 `docs/requirements.md` | C |
| 0.5 | 按第 8 节替换占位内容，配置 GitHub 与服务器，推送第一批提交 | E |

完成标准：每个人能在本机 `make deps` + `make run svc=<自己的服务>`，打开 `/docs` 看到接口，`make test` 通过。

### 阶段 1：并行开发

被依赖方的关键接口最先做真实实现，其他人靠桩开发：

| 成员 | 第一优先 | 之后 |
|---|---|---|
| A | M1 `/internal/v1/blocks` 真实实现 | 教室座位 CRUD、搜索、预约 |
| B | 前端 core 完善（通知铃铛、分页组件）、M1 页面 | 签到、提醒任务 |
| C | 提交申请、审批状态机 | 超时撤销 |
| D | 角色与用户管理 | 资格门槛、审批配置 |
| E | 测试服务器就绪、测试环境自动部署跑通 | 工单状态机 |
| F | 通知模板与站内通知查询 | 邮件发送、超时升级 |

第 3 周末的目标：测试环境自动部署可用（哪怕部分接口仍是桩）。

### 阶段 2：每周联调

每周五固定联调一次：

1. 各调用方把相应的 `STUB_CLIENTS` 切到 `false`，在测试环境跑真实调用。
2. 在 Actions 页面手动运行 Integration Test（`integration-test.yml`）对测试环境跑 `tests/integration`；它与测试环境部署共用并发组，不会在部署中途运行。链路实现后去掉对应测试的 `xfail` 标记。
3. 发现的契约不一致当场记 issue，分配负责人。

B 每周查看变异测试报告（`mutation.yml`），对存活的变异体补测试或说明原因。

### 阶段 3：附加项与发布演练

- **DSH 自然语言代理（F 主导）**：以 DSH 插件形式实现，只调用网关的公开接口（`/api/v1/...`），用户的 JWT 作为插件调用凭证；意图不明确时追问（时间、区域、教室等必填信息缺失时不执行）；插件的安装与配置写进部署流程。具体插件机制以个人 Lab 对 DeepSeek Harness 的分析为准。各模块配合检查自己的接口 `summary` 和参数描述是否足够让代理理解。时间不够时放弃，不影响主线。
- **发布演练（E 主导）**：从一台全新服务器开始完整部署至少两次，记录耗时和问题；演练一次生产回滚。

### 阶段 4：彩排

至少完整彩排两次，其中一次从全新服务器开始。

## 3. 每个任务的流程

| 步骤 | 做什么 | 产出 |
|---|---|---|
| 1. 建任务 | 用 issue 模板建任务：需求编号、范围、约束、验收标准、依赖 | GitHub issue |
| 2. 开分支 | 从最新 main 拉分支，命名 `<类型>/<模块>-<需求编号>-<简述>` | `feat/m1-REQ-M1-03-duration-limit` |
| 3. 写 spec | 小任务在 issue 里写清楚；涉及多个文件或跨模块的写 `docs/specs/<编号>.md`（模板见 `docs/specs/_template.md`） | spec |
| 4. AI 出方案 | 让 AI 读 AGENTS.md 和 spec，先给 2 个左右方案；人比较后选择。方案必须使用公共库已有能力（根 `AGENTS.md`"公共函数优先"），公共库缺少的能力先提出加入公共库。重要选择写 ADR | 方案或 ADR |
| 5. AI 小步实现 | 每次只让 AI 做一小块（一个接口、一个任务函数及其测试） | 代码 + 测试 |
| 6. 人工验证 | 运行测试；故意改坏核心逻辑确认测试失败；逐行审查（时区、权限、事务边界、并发） | 验证记录 |
| 7. 提交 | 小步提交，`<类型>(<范围>): <说明> [<需求编号>]` | commit |
| 8. 发 PR | 填写 PR 模板（AI 参与情况、人工验证方式）；CI 自动运行，CODEOWNERS 自动请人评审 | PR |
| 9. 评审合并 | `ci-passed` 通过、评审批准后 squash 合并；冲突由人解决 | main |
| 10. 自动部署 | 合并后自动部署测试环境并跑集成测试，失败第一时间修 | 测试环境 |

**动了跨模块接口或消息**：第 8 步契约检查会提示 → 运行 `make contracts` 提交快照 → CODEOWNERS 请提供方与调用方评审（任意一位批准即满足分支保护，因此调用方负责人还需在 PR 中留言确认已适配，PR 模板有对应勾选项）→ 破坏性变更需调用方确认后加 `breaking-change-approved` 标签。

**动了 schema**：PR 加 `schema-change` 标签，说明已有数据如何演化、旧版本代码能否在新 schema 上运行；A 评审。

**AI 写错的案例**：遇到 AI 的典型错误（例如混用无时区时间、测试只断言常量），记到 PR 描述里，同类问题出现两次就补进 AGENTS.md。这些记录是期末"人机协作过程"的素材。

## 4. 版本与发布

- 分支：只有 `main` 是长期分支，受保护；功能分支合并后自动删除。合并方式只用 squash，一个 PR 在 main 上对应一个提交。
- 测试环境：main 的每个提交都会部署，镜像标签是 12 位提交号。
- 测试环境验证：部署成功且集成测试通过后，该提交的镜像获得 `verified-<提交号>` 标签；没有这个标签的提交不能发布到生产。
- 生产发布：发布负责人（E 或 C，仓库管理员；`v*` 标签只有管理员能创建）在 main 上打标签 `vX.Y.Z` 并推送 → 流水线给该提交已验证的镜像打版本标签、生成 Release Notes（自动列出包含的 PR）→ 审批人（不能是触发者本人）在 Actions 页面批准 → 部署前自动备份数据库 → 部署 → 校验各服务运行的版本与提交 → 创建 Release。`v*` 标签创建后任何人都不能修改或删除；未配置生产审批人时发布直接失败。
- 回滚：Actions 页面从 main 手动运行 Deploy Prod，填入要回到的已发布版本号，同样需要审批。数据库不降级（迁移"先扩展后收缩"），需要恢复数据时用部署前的备份（`deploy/backup.sh` 注释中的恢复命令）。
- 当前版本：`http://<服务器>:8000/ops/<服务>/version`，或前端冒烟页。
- 发布顺序：compose 按依赖健康状态启动，common 与 M1 先于 M2、M3 就绪；同一环境同一时间只允许一次部署，集成测试在部署完成后才运行。

## 6. 期末演示

| 演示项 | 主讲 | 准备 |
|---|---|---|
| 从全新环境通过流水线部署 | E | 新服务器跑 `deploy/server_init.sh`，配置 secrets，手动触发部署 |

## 8. 首次提交时保留的占位与项目启动清单

仓库在首次提交时是一套可运行的样板：契约、公共库、流水线、部署与文档齐备，业务接口为桩实现。能给出默认值的配置都已给出（例如部署密钥的默认值在 `.env.example`，开发与测试的演示账号与管理员密码为 `campus123`），不需要填写即可运行。依赖具体成员或外部资源的内容保留为占位，在首次提交后由对应负责人补上：

| 占位 | 位置 | 何时补上 | 负责 |
|---|---|---|---|
| 成员 A–F 的姓名与分工确认 | 本文第 1 节 | 项目启动会 | C |
| CODEOWNERS 中的 `@member-a` 至 `@member-f` | `.github/CODEOWNERS` | 成员加入仓库后替换，再运行一次 `scripts/github_setup.sh` | E |
| 生产审批人 | `scripts/github_setup.sh` 的参数 | 成员加入仓库后带上审批人再运行一次 | E |
| ADR 状态"提议"与"达成一致的过程" | `docs/adr/*.md` | 逐条讨论确认后改为"已采纳"并补写过程 | C |
| 业务接口的桩实现 | `services/*/app/stubs.py` 与各路由 | 按各设计文档"实现顺序"逐个替换，最终删除 `stubs.py` | 各模块 |
| 集成测试中的 `xfail` | `tests/integration/` | 对应链路实现后去掉 | F |
| 服务器地址与 SSH | GitHub 环境 secrets / variables | 服务器租用后，见下表 | E |
| HTTPS | 网关 | 确定服务器与域名后（NFR-08、R-13） | E |

首次提交后的配置清单（脚本均可重复执行）：

| 步骤 | 命令或位置 |
|---|---|
| 1. GitHub 仓库规则、环境、标签 | `scripts/github_setup.sh <owner/repo> [生产审批人...]`；成员加入后带上审批人再运行一次 |
| 2. 服务器初始化（Docker、部署用户、关闭密码登录、防火墙、每日备份） | 服务器上执行 `deploy/server_init.sh <部署用户> "<公钥>"`；测试与生产共用一台服务器时追加参数 `single-server` |
| 3. 连接信息 | test / production 环境 secrets：`DEPLOY_HOST`（公网 IP）、`DEPLOY_USER`、`DEPLOY_SSH_KEY`、`DEPLOY_KNOWN_HOSTS`（核对指纹后的 `ssh-keyscan` 输出） |
| 4. 单服务器方案 | 仓库变量 `TEST_ENV_FILE=test-single-server.env` |
| 5. 可选：修改部署密钥 | 本地部署写在 `.env`；流水线部署写在 GitHub 环境 secrets，或在该环境首次部署前运行 `scripts/gen_secrets.sh test` / `production` 生成随机值 |
| 6. 可选：真实邮件 | `deploy/env/prod.env` 的 `SMTP_*` 与 production 密钥 `SMTP_PASSWORD` |
